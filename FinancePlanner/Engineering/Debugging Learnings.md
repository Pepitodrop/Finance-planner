# Debugging Learnings

Durable investigation techniques and pitfalls found via git history, not routine bug-fix detail.

## Real defects only surface via real-browser acceptance testing, not just unit tests

The Step 12 (Finance Intelligence) browser-acceptance work (git log around `0b3e790`..`75cd53c`, early Aug 2026) found several real, previously-shipped defects that unit tests had missed entirely: a legacy stylesheet still styling three pages after a redesign, interactive controls under the 44px touch-target minimum, an `AiPanel` progress fixture that never actually showed the progress screen, a `forced-colors` button border that used `:where()` and so never won the cascade. Pattern: when a redesign/consolidation lands, a real headless-browser acceptance pass over the actual rendered pages catches classes of defect (CSS specificity, cascade order, fixture wiring) that component-level unit tests structurally cannot.

## When a UI element visually overflows, measure before guessing

`.ai-result` grid column widths were fixed by *dumping actual measured column widths* (`846c82e "Diag: dump exact .ai-result column widths instead of guessing further"`) rather than iterating by trial-and-error CSS changes. The commit sequence (`837c825` → `846c82e` → `550fd50` → `752e5b9` → `88fcc7e`) shows two earlier attempted fixes that didn't fully work before the diagnostic-measurement step was added — worth reaching for a measurement/diagnostic step early rather than after repeated guesses.

## `autoFocus` timing can break focus-restoration logic silently

Accessibility test-writing (2026-08-02, `TODOS.md` "Completed" section) found that a transaction dialog's native `autoFocus` on an input fired *before* the app's own `MutationObserver`-based focus-management code (`FrontendExperience.tsx`) got a chance to capture the true trigger element as `previousFocus`. Result: closing the dialog tried to restore focus to a node that had been replaced, and silently fell back to `<body>` — no error, no visible symptom outside actual screen-reader/keyboard use. Lesson: React's synchronous `autoFocus` on commit can race a `MutationObserver`-based enhancement layer; prefer letting the enhancement layer own initial focus rather than mixing in native `autoFocus`.

## Acceptance-script flakiness is sometimes deterministic, not timing

`16a8d3f "Diagnose: retrying didn't help -- this is deterministic, need to see the hook itself"` — a useful reminder that when retrying/waiting-longer doesn't fix a flaky-looking acceptance-test failure, the next step is to inspect the actual hook/state machine involved rather than adding more retries, because the failure may be a real, repeatable state-ordering bug (in this case, a vault-conflict dialog recurring instead of being one-shot, `019e38c`).

## String-matching test assertions can flag their own expected output

Two separate incidents (`af8ab83` "fraud-language check flagged its own required denial sentence", `69ebae3` "AUTO confidence check flagged the briefing's own real percentages") — a substring/regex check meant to detect a *bad* pattern in rendered text ended up matching the deliberately-present correct text that happens to contain a similar substring. Worth double-checking that a text-pattern assertion can't self-match the correct/expected content before trusting a "found a bug" result from it.

## A CI production-acceptance failure can mask a second, deeper failure behind it

PR #131's Step 12 (Finance Intelligence) and Step 13 (Data/Subscriptions/Account) browser-acceptance jobs had been failing at their *very first* interaction for a while (a blanket `.topbar > .primary { display: none }` CSS rule hid the Finance Intelligence page's own legitimate "Manual entry" button, matching the same selector as the unrelated pages the rule was meant to fix). Fixing that one root cause let both scripts progress much further and immediately hit fresh, previously-invisible failures: stale string assertions in `scripts/auth-security-production-acceptance.mjs`, `finance-intelligence-production-acceptance.mjs`, and `data-privacy-production-acceptance.mjs` that still expected pre-redesign UI copy/behavior (a pre-auth passkey button, a collapsed test-password `<details>` form, "Reset financial data" wording, and — most importantly — a reset-confirmation dialog that was expected to promise reseeded *example data*, the exact bug the PR was fixing). Lesson: a long acceptance script failing early does not mean the rest of it is proven correct — fixing the blocking defect can surface a queue of separately-broken, previously-unreached assertions, some of which may (as here) still be actively asserting the *old, wrong* behavior rather than merely being out of date cosmetically. Re-run the *whole* script after each fix, don't stop at the first green result past the original failure point.

## Reusing a persistent local Postgres across repeated acceptance-script runs mimics real app bugs

Debugging the Step 12/13 failures above involved re-running `scripts/*-production-acceptance.mjs` directly (not via CI) against a long-lived local `postgres:17-bookworm` Docker container reused across many invocations, all sharing the same hardcoded `local-user`/`AUTH_MODE=local` identity. Real CI (`production-acceptance.yml`) gets a *fresh* Postgres service container per job run; repeated local runs against the same database accumulate that identity's cloud finance-state across runs, and a later run's fresh local vault genuinely conflicts with (and can trigger a real, code-correct `VaultConflict` → `window.location.reload()`) the earlier runs' leftover cloud state — producing a transient-looking blank-page/re-lock failure that has nothing to do with the code under test. Confirmed via instrumentation (`document.readyState`, `#root` child count, and re-checking after a delay showed the page had reloaded to "Unlock Finance Planner") and by reproducing cleanly on a *freshly recreated* Postgres container. Lesson: when manually re-running this repo's browser-acceptance scripts outside CI, recreate the Postgres container (or otherwise clear `user_finance_state`/`auth_store` for the shared local-user identity) between runs, or a real "vault conflict on shared identity" mechanism will look like a flaky/broken app.

## Destructive migration detectors must match the complete canonical record, not an ID pattern

The final review of PR #131 found that the first version of `isLegacyDemoState()` described itself as an exact untouched-demo detector but only required legacy account/goal fields plus transactions whose IDs matched `tN` and pointed at legacy accounts. A user could edit the amount, description, date, category, type, or recurring flag of an existing `t1` transaction and still be classified as untouched demo data; unlock would then replace that state with `emptyProductionState`. The corrected detector matches the exact canonical record count and every material field for accounts, transactions, and goals, rejects provider metadata and subscriptions, and has regression coverage for edited/removed/replaced/extra `tN` transactions. Lesson: any automatic cleanup that can discard user data must prove the whole disposable signature; structural hints such as prefixes, fixture-like IDs, or partial field equality are not sufficient evidence for deletion.

## A fixed-position optional banner can float on top of a screen it's deliberately meant to coexist with — suppressing it can be the wrong fix

Live mobile testing (390x844, redesign-existing-projects audit pass, 2026-08-10) reproduced a real defect: immediately after registering, `AuthGate`'s optional "Add a passkey" recommendation (`.passkey-enrolment`, fixed-position) rendered on top of `VaultGate`'s setup form and captured pointer events, making the "Turn on encryption" submit button unreachable without first dismissing the banner (confirmed via a Playwright click timing out after 30s with an explicit pointer-interception error).

**First attempt was wrong and had to be reverted.** The obvious-looking fix — mark `VaultGate`'s screen `role="dialog" aria-modal="true"` to engage the existing `body:has([aria-modal="true"]) .runtime-optional-surface { visibility: hidden; }` suppression rule (the same one `VaultConflict.tsx` uses) — got pushed, then broke CI's `scripts/auth-security-production-acceptance.mjs` Step 11 (`AUTH-05`). That script's own comment states the intended design explicitly: the passkey banner is *deliberately* "shown alongside VAULT-01's setup screen underneath, matching the real runtime-surface composition" — it's supposed to coexist and stay dismissable there, not disappear. Suppressing it entirely satisfied the overlap symptom but violated a real, already-tested product requirement. A quick "click now succeeds" check is not sufficient evidence a fix is correct — check whether the *existing* behavior you're changing is itself asserted somewhere (grep the acceptance scripts) before assuming a visual conflict should be resolved by hiding one side.

**Correct fix:** take the banner out of `position: fixed` specifically when it coexists with `.vault-screen` (`body:has(.vault-screen) .passkey-enrolment { position: static; ... }`), so it flows in-document above the vault card and pushes it down instead of floating over it — an overlap becomes structurally impossible regardless of scroll position or content height, and the banner stays fully visible/dismissible exactly as `AUTH-05` requires.

**A second false positive along the way:** a naive `getBoundingClientRect()` overlap check after `padding-bottom`-based clearance attempt showed no overlap once scrolled to the absolute page bottom, and Playwright's own `.click()` even succeeded — but a real `document.elementFromPoint()` hit-test at the button's actual on-screen center (after only a `scrollIntoView({block:'nearest'})`, the realistic amount of scroll a real interaction would produce) still showed the banner on top. Bounding-box math and a passing scripted click are not reliable proxies for "a real tap lands on the right element" — `elementFromPoint` at the exact interaction coordinates is the authoritative check, and it's exactly what the corrected `scripts/auth-security-production-acceptance.mjs` regression assertion (`obstructsVaultSubmit`) now does.

Lesson: this class of "optional overlay floats over a screen's own primary action" bug is invisible in jsdom/unit tests (no real layout engine, no `:has()` CSS application) — it only reproduces in a real browser at real viewport widths, and any fix needs the same real-browser, real-coordinate verification (not just "the DOM contains it" or "a scripted click succeeded") before being trusted.
