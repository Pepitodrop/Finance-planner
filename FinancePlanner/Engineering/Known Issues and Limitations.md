# Known Issues and Limitations

Distinguishing real product gaps from unverified provider integrations (the latter are covered in more detail in [[Provider Status]]).

## Real, currently-open gaps (from `TODOS.md` "Infrastructure" / open items, still true as of bootstrap)

- **`VERSION` file is disconnected from actual versioning and doesn't match anything.** Found during `/document-release` (PR #131, 2026-08-11): the root `VERSION` file reads `0.1.1.0`, `package.json` reads `0.2.0`, `server/package.json` reads `0.1.0`, and `CHANGELOG.md`'s latest tagged entry is `[0.3.0]` — four different numbers, none matching. No script or GitHub Actions workflow reads `VERSION` at all (`grep`-confirmed empty across `scripts/*.mjs` and `.github/workflows/*.yml`), so it isn't wired into any real release process; it's likely a vestigial file from an earlier/different tooling setup. Pre-existing on `main`, unrelated to PR #131's own changes (confirmed via `git diff origin/main...HEAD -- VERSION`, empty) — left untouched rather than guessing at a "correct" number without a clear source of truth; whoever owns actual releases should reconcile or remove it.

- **COBOL tests need the GnuCOBOL runtime locally.** 4 tests in `server/test/cobol-engine.test.js` fail in sandboxes lacking the GnuCOBOL runtime. Re-verified fresh during `/ship` (PR #131, 2026-08-11): the compiled binary (`build/transaction-rules`) is present in this sandbox, but invoking it fails with `error while loading shared libraries: libcob.so.4: cannot open shared object file` — a missing shared-runtime-library failure, not a missing-binary/`ENOENT` failure as previously recorded here. CI installs the full GnuCOBOL toolchain (runtime included) and its `cobol` check passes — independently re-confirmed green at HEAD `c7272c0a6301b73b61935cf15c71e7baa4aa9de5` during this same `/ship` phase. Real gap for any dev sandbox lacking `apt-get`/root to install `libcob`. See [[COBOL Domain Core]].
- **Single JS bundle, no code-splitting.** ~992 kB (271 kB gzip) single chunk; all routes ship before first paint. Deferred as a risky wide refactor, not attempted opportunistically.
- **`vitest@2.1.9`'s bundled dev toolchain has known CVEs** (dev-server only; `npm audit --omit=dev` is clean). Needs a `vitest@4.x` major bump, not yet done.
- **No server-side full data export.** Account deletion is complete; data export (`src/backup.ts`) is client-side-only and only covers loaded `AppState`, not server-only records (session revocations, connector metadata). Scoped as a future feature, not a hardening fix.
- **Alertmanager has no real paging receiver.** `ops/monitoring/alertmanager.yml` ships only a stub; alert rules are real and will fire into nothing until an operator wires a real destination.
- **Disconnect can lose the ability to retry a failed provider revocation.** Found by an outside-voice (Codex) review during `/plan-eng-review` on PR #138 (2026-08-18): `server.js`'s disconnect handler calls `store.remove()` unconditionally, even when `GoCardlessProvider.disconnect()` reports `providerRevoked: false`. A transient network failure during disconnect deletes the only local record (`requisitionId`) that would let a retry ever close the requisition — the consent stays live at GoCardless until it expires naturally. Deliberately not fixed in PR #138 to avoid scope creep (needs new state modeling plus a retry trigger this codebase doesn't have); see the TODOS.md "Connections" section and [[Provider Callback Binding]].
- **`connector_connections`/`oauth_nonces`' provider CHECK constraint never included `'google-subscriptions'`.** Found 2026-08-20 while widening the same constraint to add `'enablebanking'` (migration `009_enable_banking_provider.sql`): the original constraint (migration `001_connector_store.sql`) only allows `gocardless`/`finapi`/`paypal`, but `google-subscriptions-router.js` writes to the same `store` instance (confirmed: `server.js` passes the same `store = persistence.store` into `createGoogleSubscriptionsRouter`) using `provider = 'google-subscriptions'`. On a Postgres-backed deployment, `createConnectionSetup()`/`registerOAuthNonce()` calls for Google Subscriptions would fail the CHECK constraint outright. Deliberately **not fixed** as part of the Enable Banking work (unrelated bug, would have expanded that PR's scope) — flagged here for a dedicated fix.
- **A concurrent disconnect can be overwritten by an in-flight `completeCallback()`/`finalizeConnection()`.** Found during the independent `/code-review` pass on PR #142 (2026-08-19/20) while auditing callback replay protection and reconnect-preservation: the two-phase callback route (`consumePendingConnectionSetup()` → `providerAdapter(provider).completeCallback()` → `finalizeConnection()`, `server/src/server.js`) burns the single-use nonce before the provider-side network exchange runs, so a `DELETE /api/connectors/:provider` that lands while that exchange is in flight can be silently overwritten when `finalizeConnection()`'s upsert completes afterward. For GoCardless/PayPal this window was one local DB write wide under the old single-step `activateConnection()`; Enable Banking's `completeCallback()` (`server/src/providers.js`) added a real network call (`POST /sessions`, up to `DEFAULT_TIMEOUT_MS` plus retries) in between, widening the window for every provider on the shared route. Deliberately not fixed as part of this review pass to avoid scope creep — needs either an optimistic-concurrency version column on `connector_connections` or a disconnect-tombstone `finalizeConnection()` checks, neither of which exists yet. See [[Provider Callback Binding]] and the TODOS.md "Connections" section.
- **A parallel, apparently-dead "client-side bank runtime" module cluster exists alongside the real one.** Found while updating the vault during PR #138's `/plan-eng-review` continuation (2026-08-18): `src/bankRuntime.ts`, `src/bankCallbacks.ts`, `src/bankWebhook.ts`, `src/bankWebhookHttp.ts`, and `src/gocardlessBankProvider.ts` each have their own passing test suite, but `grep`-confirmed (excluding each file's own test) **zero consumers anywhere else in `src/` or `server/`**. The actual production Connections/webhook flow runs entirely through `server/src/providers.js`, `server/src/server.js`, `server/src/webhook-security.js`, `src/features/connections/ConnectionsPage.tsx`, and `src/connectors.ts` — a completely separate, unrelated implementation. This looks like a superseded earlier design iteration left in the repo; its passing tests give a false impression of live, exercised infrastructure (the vault's own [[Connections Page]] note previously and incorrectly listed `bankCallbacks.test.ts` as related coverage — corrected). Deliberately not touched in PR #138 (user decision, 2026-08-18): document only, don't delete — removing ~5 files with their own test suites is a separate decision with its own blast radius.

- **`connectionsScrollLayout.test.ts` has never actually exercised real CSS — Vitest's `css: false` default no-ops the `import './connections.css'` it relies on.** Found 2026-08-21 while working on `feat/bank-discovery-ux` and re-running the full suite: this test asserts `getComputedStyle(dialog).display === 'flex'`, but the real rule (`.modal.connections-setup-modal { display: grid; ... }`) has been `display: grid` since PR #143 (2026-08-13) — confirmed by reproducing the identical failure on a clean `origin/main` checkout via `git stash`, before touching any code. No `css: true`/`css: { include: ... }` option exists in this repo's Vitest config, so jsdom never receives the imported stylesheet at all — `getComputedStyle` falls through to the browser UA default (`block` for a `<section>`), which is exactly the observed failure (`expected 'block' to be 'flex'`), not a `flex`-vs-`grid` mismatch. This means the test has given false confidence about the "exactly one scroll region" contract ([[Connections Page]]) since it was written; the real evidence for that contract is the project's own `scripts/connections-production-acceptance.mjs` real-browser run (confirmed still passing locally on `feat/bank-discovery-ux`, 2026-08-21: 14/14 modes, real Chromium, real Postgres-backed server). Deliberately not fixed as part of `feat/bank-discovery-ux` (unrelated Vitest-config bug, would have expanded that branch's scope) — needs either a Vitest `css` config change or rewriting the test to assert against the stylesheet source text instead of `getComputedStyle`.

- **A shared "sensitive" rate-limit bucket let a decorative feature deny a security-sensitive one (found live 2026-08-21, fixed).** Every route under `/api/connectors/` — including the newly-added, purely decorative institution-logo proxy — shared one 20/min-default sensitive bucket with `POST /start`, sync and disconnect. Browsing a real Enable Banking directory during a temporary production deployment generated enough logo requests to exhaust that bucket by itself, returning 429 "Too many requests" on `POST /start` for the same client and blocking the user from ever reaching consent. Fixed with a dedicated third rate-limit tier for the logo route (`ASSET_RATE_LIMIT_PER_MINUTE`, default 240/min) — see [[Rate Limiting]]. Not yet re-verified live.

## Product-level gaps stated in README ("Remaining production gaps")

- representative Playwright, accessibility, load and physical-device test matrices
- independent threat model, penetration test and privacy review
- formal data-retention, account-deletion and recovery workflows (deletion itself is implemented; the surrounding formal workflow documentation is not)
- managed monitoring, tracing, SLOs and paging
- live GoCardless/PayPal certification and reconciliation testing
- safe multi-instance coordination for the encrypted whole-document auth store
- permanent Android release key, verified Digital Asset Links and Play Store publication
- native iOS and signed desktop packages
- representative AI quality, latency, drift and safety benchmarks

## Not a product gap — a testing-evidence gap

Several CI workflows are **credential-gated and non-blocking by default** (`hosted-ai-acceptance.yml`'s `require_live_ai`, `runtime-canaries.yml`'s `require_all`, `production-operations.yml`'s `require_live_bank`). A fully green CI run does **not** by itself prove GoCardless, PayPal, hosted HF inference, or Google OAuth work end-to-end in production — that evidence is deliberately deferred to a manual, human-recorded process (`docs/issue-105-live-verification.md`). Don't conflate "CI is green" with "the integration is live-verified." See [[Provider Status]].
