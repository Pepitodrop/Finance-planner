# Connections (page)

Secondary nav, "Connections" group. Bank (GoCardless) and PayPal connection management — institution selection, consent redirect, sync status, disconnect. Not separately routed per sub-step; represented as UI states within this one page.

- **Component:** `src/features/connections/ConnectionsPage.tsx`, `src/ConnectionsPanel.tsx`
- **Model:** `src/features/connections/connectionsModel.ts`
- **Backend:** [[providers.js]] `OpenBankingProviderRegistry`
- **Providers:** [[GoCardless]], [[PayPal]]
- **Flows:** [[Bank Connection Flow]], [[Bank Consent Flow]], [[Bank Sync Flow]], [[Bank Disconnect Flow]], [[PayPal Redirect Flow]]
- **COBOL boundary:** [[Banking Core Module]]
- **Institution lookup:** `src/institutions.ts` (static picker catalogue/icons/categories) + `src/connectors.ts` `fetchProviderInstitutions`/`fetchProviderStatus` (live, server-validated directory + availability — see [[Provider Institution Selection Contract]])
- **Institution visual identity:** `src/institution-logos.ts` — reviewed Simple Icons CDN marks for PayPal/N26/Commerzbank/Deutsche Bank/Sparkasse, an original Finance Planner lettermark (never a bank's real brand color) for every other institution, with graceful `onError` fallback
- **Related tests:** `src/features/connections/connectionsModel.test.ts`, `src/features/connections/ConnectionsPage.test.tsx`, `src/institution-logos.test.ts`, `src/bankConnection.test.ts`, `src/app/navigation.test.ts` (return-detection tab routing)
- **UI structure (reworked 2026-08-13):** setup dialog is a single scroll region (fixed header/progress, `.connections-setup-content` scrolls) instead of nested scrollbars; the institution list is one bordered surface with row separators instead of individually outlined rows; category pills scroll full-bleed so the first/last is never clipped; the search box uses one `:focus-within` treatment on the wrapper, deliberately compounded with `.modal` in the selector so a same-specificity rule from another stylesheet loaded later can't reintroduce a second nested border (see [[Provider Institution Selection Contract]] sibling note in `connections.css` comments). Provider-start errors render with `role="alert"` inside the active step (setup modal / attention screen) instead of behind the modal, and clear on institution change, back, or close.
- **Provider availability (added 2026-08-14, verified still correct 2026-08-18):** `providerStatus` is an explicit `loading|error|ready` union — a "Checking availability…" badge appears per-institution while loading, a dismissible `role="alert"` banner with a Retry action appears on failure; external providers fail closed in both states (manual accounts unaffected). Retry (2026-08-18) uses a request-generation counter so a stale response can never overwrite a newer one, even though the Retry button itself can't practically be double-clicked (it only renders during `status === 'error'`, so a click immediately unmounts it).
- **Callback/return handling (fixed 2026-08-18):** landing back from a real provider return (or a failed callback) now correctly boots into this page — see [[Provider Callback Binding]] for the routing fix and `src/app/navigation.test.ts`'s `initialTabFromSearch` coverage. Previously this likely never happened automatically for GoCardless or PayPal-partner, and possibly not for PayPal-owner either.
- **Correction:** this note previously listed `src/bankCallbacks.test.ts` as related coverage. Verified 2026-08-18 that `bankCallbacks.ts` (and the sibling `bankRuntime.ts`/`bankWebhook.ts`/`bankWebhookHttp.ts`/`gocardlessBankProvider.ts` cluster) has no consumer anywhere outside its own test file — it does not exercise this page's actual code path. See [[Known Issues and Limitations]].
- **Provider resolution (added 2026-08-20):** picking a bank tile no longer implies GoCardless — `chooseInstitution()` resolves the concrete AIS provider ([[Enable Banking]] preferred, [[GoCardless]] fallback) once, transparently, before any bank-specific network call, and fixes it in `resolvingProvider` state for the rest of that attempt. No "choose your aggregator" screen. If the preferred provider's live search for a bank comes back empty (or errors) and the fallback is independently available, an explicit "Try another connection method" action appears in the resolution step — user-initiated only, never automatic, and only reachable before `startConnector()` is ever called (that call is a full-page navigation, so nothing can retarget an in-flight attempt afterward). `displayName: 'Bank connection'` for Enable Banking, matching the page's existing bank-centric copy — the resolution step's own subtitle no longer names any aggregator either.
- **Found and fixed during this same work (2026-08-20):** `loadLiveInstitutions()`'s "don't refetch a directory we already have" guard used `liveInstitutions` truthiness, but an empty array (a legitimate "this provider has nothing for this country" result) is truthy in JS — switching `resolvingProvider` without an explicit override would have silently kept showing the *previous* provider's stale directory. Fixed with a `{force: true}` option used exactly where the resolved provider actually changes.
- **Bank-family directory resolution (fixed 2026-08-21):** choosing a family picker tile ("Volksbank / Raiffeisenbank", "Sparkasse") no longer prefills the live branch search with that literal umbrella label (a real, reported bug — the label never matches a real ASPSP name). The resolution step's blank-query view is now a family-scoped subset of the live directory (`institutions.ts`'s `directoryTerms`, matched against name/BIC/Enable Banking's `group.name`), falling back to the full directory (with an explicit "wasn't found under this connection method" notice, not a silent scope change) when nothing narrows. A new top-level "search the full bank directory" action lets a concrete bank not in the 11-entry static catalogue be found directly. See [[Bank Family Directory Resolution]] for the full mechanism, structural PayPal-inspiration boundary, and verification state.
- **Verification state:** implemented / **not runtime or production verified** — see [[Provider Status]]. The 2026-08-21 institution-discovery UX change specifically: unit/component-verified and locally browser-verified for the surrounding modal/scroll/mobile mechanics (see [[Bank Family Directory Resolution]]); the resolution screen itself has no live-provider browser run in this environment (no AIS credentials configured).

- **Real bank logos (added 2026-08-21, LIVE VERIFIED same day):** concrete live bank rows and the Step 3 redirect-confirmation header now show the bank's real logo (via [[Institution Logo Proxy]]'s same-origin proxy) instead of always falling back to a Finance Planner lettermark, with a safe fallback order and no CSP change. A temporary production deployment confirmed real cooperative-bank logos rendering and `GET /api/connectors/enablebanking/logo` returning 200 live.
- **Rate-limit interaction (found + fixed 2026-08-21):** the logo proxy's own requests briefly shared Finance Planner's sensitive rate-limit bucket with `POST /start`/sync/disconnect, so browsing a real bank directory could exhaust it and return 429 on those genuinely sensitive routes. Fixed with a dedicated tier — see [[Rate Limiting]].
- **Embedded Auth Flow widget (added 2026-08-22):** Step 3's post-confirm view for Enable Banking now renders the official `<enablebanking-auth-flow>` widget inside this page's own modal instead of navigating to a full-page Enable Banking-hosted redirect — the "secure bank authorization" sub-step keeps Finance Planner's dark/glossy identity, existing modal geometry, and PR #143's Firefox scroll fix. GoCardless/PayPal are unaffected (still redirect immediately). See [[Enable Banking Auth Flow Widget]] for the full architecture, security review, and browser-QA evidence.
- **Provider authorization popup + `PopupWaitingStep` (added/fixed 2026-08-25):** in production, `startProvider()` no longer treats a successful popup launch the same as an actual same-tab redirect. `startConnector()` now returns a distinct `{mode: 'popup', attempt}` result (previously `{mode: 'redirect'}`, the same value used for a real navigation), which this page renders with a dedicated `PopupWaitingStep` at Step 3: clears `busy` (a real popup never navigates this tab away, so leaving the modal permanently busy — the original bug — had no way to ever resolve on its own) and shows "Bank authorization opened in a secure window. Complete it there; Finance Planner will update automatically when it returns." Cancel, the Step-3 Back arrow, closing the setup dialog, and switching institutions all call `abandonConnectorPopupAttempt()` (closing the real window and its `sessionStorage`/`localStorage` bridge records). If the browser blocks the popup or can't create the tab-local return binding, `startConnector()` now rejects **before** contacting `/start` — this page's existing generic `onError`/`busy=false` catch path surfaces that as a normal, retryable start failure (e.g. "Bank authorization needs a separate secure window. Allow pop-ups for Finance Planner and try again."); it does **not** fall back to a same-tab redirect or the embedded widget, since either would unload this page and destroy the in-memory vault key.
  - **Fixed 2026-08-25 (third PR #154 review round, same day):** this step originally also polled `attempt.popup.closed` every 500ms to auto-detect a manually-closed popup, offering "Try again" only once detected. Removed entirely — Finance Planner's `Cross-Origin-Opener-Policy: same-origin` header makes `.closed` unreliable once the popup navigates cross-origin (it can read `true` while the real window is still open), and every poll this page ever performed happened strictly after that point. "Try again" is now always available (not conditioned on any detected state) and explicitly abandons the current popup before starting a fresh one, so a user-initiated retry can never leave two concurrent authorization attempts running. See [[Provider Authorization Popup Bridge]] for the full bridge architecture, its bug history (including a since-reverted attempt to fall back on a blocked popup, and this `.closed`-polling removal), and current verification state.

- **Persisted connection survives page navigation (fixed 2026-08-27, PR #154, seventh Mock ASPSP pass):** `connections` was plain React state, destroyed on unmount — navigating to Subscriptions and back made a genuinely still-connected "Bank connection / Connected" card disappear even though nothing was ever disconnected server-side (a live-reproduced defect, not a hypothetical). `GET /api/connectors` only ever returned provider descriptors, never the user's own persisted connector rows, so a fresh mount had no way to learn a connection already existed without a full provider synchronization. Fixed with a new read-only `GET /api/connectors/connections` (`listStoredConnections()` in `server.js`, reusing the same secret-free `connection()` summary `buildSyncPayload()` already trusts), fetched on mount independently of provider-status loading and never triggering a provider sync merely to list what's stored. A functional state updater ensures a fresher post-sync `connections` value from an in-flight `synchronize()` call is never clobbered by this mount-time snapshot resolving later.
  - **Found by adversarial review, fixed same pass:** the mount fetch could still resolve *after* a disconnect that happened while it was in flight (server-side `listStoredConnections()` awaits each provider sequentially, so it can be slower than a single-provider disconnect), which would have resurrected the just-disconnected connection in the UI. Fixed by tracking disconnected providers for the lifetime of the mount and filtering them out of whatever the stale fetch returns.
  - **Status: code-fixed, test-verified only (5 tests in `ConnectionsPage.test.tsx`'s "persisted connections survive page remount" suite, including a deterministic reproduction of both races via controlled promises) — not yet live-verified.**
- **Reconnect reconciliation UX (added 2026-08-27):** the sync-selection screen now labels a reconnect-matched account "Already in Finance Planner — refreshing balance" instead of presenting it identically to a genuinely new discovery — see [[Stable Account Identity and Reconnect Reconciliation]] for the live reconnect-duplication defect this reconciliation fixes and why an ambiguous-but-safe merge must still be visible to the user, not silent.
- **Restore a removed provider account (added 2026-08-27, PR #154, independent review "Blocker 1"):** the "Manage connection" screen (`AttentionScreen`) now renders a "Removed accounts" section listing every account this connection has excluded (display name + a "Restore" button per row) whenever a connection's `excludedAccounts` is non-empty. Restoring calls `DELETE /api/connectors/:provider/exclusions/:stableAccountId` (`restoreProviderAccount()`), which only deletes the durable exclusion record — it never guesses old local transactions back into existence; the account reappears the next time this connection actually syncs, through the normal reviewed import path. A per-row busy state prevents duplicate Restore clicks on the same account; a failure shows an actionable `role="alert"` error and leaves the row listed. This exists because exclusions are now durable and independent of the live connector credential (see [[Stable Account Identity and Reconnect Reconciliation]]) — "Remove account" must never be an irreversible hidden tombstone.
  - **Found and fixed by a second review pass, same day:** `excludedAccounts` was originally attached only by the mount-time `GET /api/connectors/connections` overview, but `synchronize()` unconditionally replaces the whole `connections` array with the sync response instead — so the "Removed accounts" section silently disappeared right after any sync (manual "Refresh all" or the automatic post-provider-return sync), exactly when a user was most likely to check it. Fixed by also attaching `excludedAccounts` to every connection object `buildSyncPayload()` returns, server-side, on both its success and failure branch.
- **Routine refresh applies automatically; Choose-accounts screen now surfaces two more warnings (fixed 2026-08-27, PR #154, third independent review, "Blocker 1"/"Blocker 2"):** `synchronize()` previously only applied anything (via `onApply`) when the sync discovered a genuinely new or reconnected account — an ordinary "click Refresh" on an already-connected account (same session, no reauthorization) could silently update nothing at all, reporting "No new accounts were found." even when a real new transaction existed. Fixed: routine account/transaction updates (see `SyncPreview.routineAccountUpdates`/`transactionsToUpdate` in [[Stable Account Identity and Reconnect Reconciliation]]) apply immediately and automatically, never gated behind the selection screen a genuinely new/reconnected account correctly still requires. Two new banners were added to `SyncSelectionScreen` itself (not merely the overview `message`, which only renders on the overview screen and would otherwise go unseen while this screen is up): a note when other accounts were refreshed automatically in the same batch, and a warning when an existing account for this connection could not be automatically reconciled and might be a duplicate of a new account about to be imported.
  - **Found and fixed by an adversarial review of the same diff, same pass:** the unreconciled-legacy-account warning was originally scoped by provider only (`connector:${provider}:` id prefix), which would have (1) false-flagged accounts belonging to a completely different, still-live connection of the same provider, and (2) nagged forever on an account whose connection the user genuinely disconnected but which lacks a `stableId` (with no way to ever silence it, since removal itself requires that same `stableId`). Narrowed to `institutionId` equality between the account and the connection; an account is never flagged when either side lacks `institutionId`.
  - **Status: code-fixed, test-verified only (`ConnectionsPage.test.tsx`'s "synchronization preview and account selection" suite, including a real stateful-wrapper test proving a routine refresh survives, unduplicated, a later Choose-accounts confirmation for other accounts in the same batch) — not yet live-verified.**
