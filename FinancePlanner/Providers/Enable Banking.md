# Enable Banking (provider)

- **Implemented:** yes — real Enable Banking (https://enablebanking.com) AIS API client, `server/src/providers.js` `EnableBankingProvider`, `server/src/enable-banking-jwt.js` for RS256 application-JWT signing. Verified against current official Enable Banking docs (`/docs/api/quick-start/`, `/docs/api/reference/`) during implementation, not from memory.
- **Configured:** optional (`ENABLE_BANKING_APPLICATION_ID` + `ENABLE_BANKING_PRIVATE_KEY_FILE` or `ENABLE_BANKING_PRIVATE_KEY`)
- **Mocked:** server-side tests mock `fetch`, never a real Enable Banking sandbox call — see [[Provider Status]]
- **Role:** preferred AIS provider for normal bank connections — see [[Bank Connections]] for the Enable Banking → GoCardless preference order and fallback policy
- **Server adapter:** [[providers.js]]
- **UI:** [[Connections Page]] (bank-centric; `displayName: 'Bank connection'`, never surfaces "Enable Banking" to the user)
- **Auth model (distinct from GoCardless/PayPal):** an RS256-signed application JWT (`kid` = application id, `iss: enablebanking.com`, `aud: api.enablebanking.com`), signed fresh per request with `node:crypto` directly — no `jsonwebtoken`/`jwa` dependency added. Private key never leaves the server, never logged, resolved from a file path (preferred) or a raw env var, fails closed on anything unparseable as an RSA key (`EnableBankingConfigError`, message never includes key material).
- **Consent/callback shape (distinct from GoCardless/PayPal):** GoCardless and PayPal owner mode have their entire credential known at `start()` time. Enable Banking's flow is redirect → authorization code → a server-side `POST /sessions` exchange that only happens *after* the callback lands — this is why `OpenBankingProvider` gained a `completeCallback()` lifecycle method (identity pass-through for every other provider) and why `activateConnection()` was split into `consumePendingConnectionSetup()`/`finalizeConnection()`. See [[Provider Callback Binding]] for the full mechanism and why it doesn't weaken any of that note's existing guarantees.
- **Institution identity:** Enable Banking has no single opaque institution id — an ASPSP is identified by the compound `{name, country}` pair. `EnableBankingProvider` mints its own opaque id (`${country}:${name}`) for the picker/`institutionId` contract, decoded and re-validated against the live `/aspsps` directory in `start()` — same anti-guessing, no-`[0]`-fallback contract as GoCardless. See [[Provider Institution Selection Contract]].
- **ASPSP `group` field (confirmed 2026-08-21 against the current official API reference, `enablebanking.com/docs/api/reference/`):** the `/aspsps` response's ASPSP object carries an optional `group: { name, logo }` (`ASPSPGroup`) for cooperative banking networks — e.g. every Volksbank/Raiffeisenbank branch and every Sparkasse in a country shares one `group.name` (confirmed example: `"Volksbanken Raiffeisenbanken"`). No `service`/`psu_type` query parameter filters by group; grouping is directory metadata only, resolved client-side. `sanitizeEnableBankingAspsp()` now passes `group` through sanitized to exactly `{name, logo?}`, same allowlist discipline as every other field. See [[Bank Family Directory Resolution]] for how the frontend uses it.
- **Read-only enforcement:** `POST /auth` never sends a `payments` field — this is what actually enforces AIS-only, not directory filtering (the current docs don't confirm a `service=AIS` filter parameter's enum values, so nothing relies on one existing).
- **GnuCOBOL boundary:** routes through the same `core.validateProviderConsent`/`normalizeProviderAccountType`/`normalizeProviderAmount`/`validateProviderReconciliation` calls as every other provider. Confirmed during implementation that `VALIDATE-PROVIDER-CONSENT`'s existing generic (non-`gocardless`) branch in `core/cobol/banking/banking-core.cob` already maps Enable Banking's `AUTHORIZED` session status correctly, and the account-type/amount normalization operations take no provider argument at all — **zero COBOL source changes were needed**. See [[COBOL Domain Core]].
- **Sync pagination:** `GET /accounts/{uid}/transactions` follows `continuation_key` with `date_from`/`date_to` held identical across pages (Enable Banking's documented requirement), bounded by a safety cap (`MAX_ENABLEBANKING_PAGES`) against a provider-controlled infinite loop.
- **Sync freshness (fixed 2026-08-20):** `sync()` refreshes the account list and consent expiry from the `GET /sessions/{id}` response it already fetches for the status check, rather than the snapshot frozen at `completeCallback()` time — found by an independent `/code-review` pass on PR #142. Before this fix, an account added or removed at the bank after initial connection was never reflected, and a consent window the provider extended/shortened silently drifted from the locally cached value. Falls back to the stored values when a given response omits either field.
- **Reconnect (fixed 2026-08-20):** `start()`'s returned credential was missing `institutionId`, so a stored connection had nothing to resubmit and Reconnect was unconditionally broken for every Enable Banking connection from the moment this provider was added. Also found by the same independent review pass; fixed and covered by a "Reconnect round-trip" regression test.
- **Disconnect:** `DELETE /sessions/{id}`, idempotent on 404, never a false-positive `revoked: true` — same contract as [[GoCardless]]'s `disconnect()`.
- **Test coverage:** `server/test/enable-banking-jwt.test.js`, `server/test/enable-banking-directory.test.js`, `server/test/enable-banking-callback.test.js`, `server/test/enable-banking-sync.test.js`, `server/test/enable-banking-disconnect.test.js`, plus `server/test/open-banking-server-boundary.test.js`/`postgres-store.test.js`/`crypto-store.test.js` for the shared two-phase callback contract, and `src/features/connections/connectionsModel.test.ts`/`ConnectionsPage.test.tsx` for the frontend preference/fallback resolution.
- **Runtime verified (updated 2026-08-21):** partial. PR #144 was temporarily deployed to production (`finance.luisbenedikt.de`) against the real configured Enable Banking sandbox application. Live-confirmed: `GET /aspsps` (592 real DE institutions, real BICs, e.g. Aachener Bank, Berliner Volksbank, Volksbank Köln Bonn, Volksbank Rhein-Erft-Köln), the bank-family directory resolution/search UX (see [[Bank Family Directory Resolution]]), and reaching the Step 3 redirect-confirmation screen for an exact selected bank. **Not** live-confirmed: `POST /auth` (failed — see the fixed `maximum_consent_validity` unit bug below, not yet re-verified), consent, callback, `POST /sessions`, sync, disconnect. See [[Provider Status]] for the full matrix.
- **`POST /auth` bug found and fixed (2026-08-21):** `start()` compared `match.maximum_consent_validity` directly against a day count via `Math.min(requestedDays, maxDays)`, but the current official API reference documents this ASPSP field as an integer number of **seconds**, not days. Since a seconds value is numerically far larger than any realistic day count, the per-ASPSP clamp never actually fired — every request silently asked for the full configured default (90 days) regardless of what the selected bank's ASPSP actually supports, and Enable Banking rejects `access.valid_until` once it exceeds `now + maximum_consent_validity` (their documented constraint). This is the most plausible explanation for the live "Internal server error" observed selecting Volksbank Köln Bonn and pressing "Continue securely" (request reference `ce5c436c-f94c-43f6-8a70-b5cdd4895a02`) — plausible and well-evidenced against the code and current docs, but **not confirmed via production logs**, since none were accessible to the session that made this fix. Fixed by converting to milliseconds throughout (`server/src/providers.js`); also added `access.balances`/`access.transactions: true` to the `/auth` request body to match what the Connections UI already tells the user they're granting (previously only implicit accounts-list access was requested), and captured a safe, server-log-only provider error code/message on `jsonFetch()` failures (`error.providerCode`/`error.providerMessage`, never sent to the client) so a future provider-contract rejection is diagnosable instead of an opaque "Internal server error". Covered by new/updated tests in `server/test/enable-banking-callback.test.js`. **Not yet re-verified live** — requires another temporary deployment to confirm.
- **Real bank logos (added 2026-08-21):** see [[Institution Logo Proxy]] for the full architecture, security-review findings (one CRITICAL timeout/hang bug found and fixed), and verification state. Short version: a same-origin logo proxy re-resolves the institution server-side and re-validates the provider's own logo URL before ever fetching it, so the CSP needed **no change at all** and the browser never loads an image directly from a provider-controlled host.
- **Provider/device verified:** partial (see above) · **Production verified:** partial (directory/discovery only, see above)
- **Known blocker:** same class of gap as [[GoCardless]] — no completed end-to-end consent→sync→disconnect cycle evidenced against a live Enable Banking sandbox. Requires Control Panel setup (sandbox application, an allowed callback URL of `{APP_ORIGIN}/api/connectors/callback`, `ENABLE_BANKING_APPLICATION_ID`, and the RSA private key) before any real verification can begin.
- **Deployment wiring (added 2026-08-20, runtime-verified 2026-08-21):** `compose.yaml`'s `connector` service now passes `ENABLE_BANKING_APPLICATION_ID` from the host environment and sets `ENABLE_BANKING_PRIVATE_KEY_FILE` to a fixed in-container path (`/run/secrets/enable-banking-private-key.pem`), populated by a read-only bind mount whose host source is `${ENABLE_BANKING_PRIVATE_KEY_HOST_FILE:-./deploy/enable-banking-private-key.placeholder}` — the placeholder (committed, no key material) keeps `docker compose up` working for deployments that leave Enable Banking unconfigured; `bind.create_host_path: false` makes a mistyped real host path fail loudly at `up` time instead of Compose silently mounting an empty directory. Documented in `.env.example`. Originally only `docker compose config`/`create` were checked (this sandbox's own Docker daemon blocked entrypoint `exec` at the time). **Now runtime-verified**: PR #144's temporary deployment to `finance.luisbenedikt.de` successfully read the real key through this exact mount and signed working application JWTs — confirmed by `GET /aspsps` succeeding live against the real Enable Banking sandbox (592 institutions returned). (Separately, a later session's own sandbox was able to run real Docker containers, including a full local production-acceptance harness run — see [[Connections Acceptance]] — suggesting the earlier Docker limitation was specific to that prior session's environment, not a durable constraint.)

- **Institution-discovery UX (fixed 2026-08-21):** the picker's "Volksbank / Raiffeisenbank" and "Sparkasse" tiles used to prefill the live branch-search box with that literal umbrella label, which never matches a real ASPSP name ("Volksbank Demmin", "Raiffeisenbank Grävenwiesbach", ...) — a real, reported UX defect, not a security one (the anti-guessing `institutionId` contract above was never affected). Fixed in `src/institutions.ts`/`connectionsModel.ts`/`ConnectionsPage.tsx` — see [[Bank Family Directory Resolution]] for the full mechanism and verification state.
