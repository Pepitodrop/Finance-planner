# Enable Banking (provider)

- **Implemented:** yes — real Enable Banking (https://enablebanking.com) AIS API client, `server/src/providers.js` `EnableBankingProvider`, `server/src/enable-banking-jwt.js` for RS256 application-JWT signing. Verified against current official Enable Banking docs (`/docs/api/quick-start/`, `/docs/api/reference/`) during implementation, not from memory.
- **Configured:** optional (`ENABLE_BANKING_APPLICATION_ID` + `ENABLE_BANKING_PRIVATE_KEY_FILE` or `ENABLE_BANKING_PRIVATE_KEY`)
- **Mocked:** server-side tests mock `fetch`, never a real Enable Banking sandbox call — see [[Provider Status]]
- **Role:** preferred AIS provider for normal bank connections — see [[Bank Connections]] for the Enable Banking → GoCardless preference order and fallback policy
- **Server adapter:** [[providers.js]]
- **UI:** [[Connections Page]] (bank-centric; `displayName: 'Bank connection'`, never surfaces "Enable Banking" to the user)
- **Auth model (distinct from GoCardless/PayPal):** an RS256-signed application JWT (`kid` = application id, `iss: enablebanking.com`, `aud: api.enablebanking.com`), signed fresh per request with `node:crypto` directly — no `jsonwebtoken`/`jwa` dependency added. Private key never leaves the server, never logged, resolved from a file path (preferred) or a raw env var, fails closed on anything unparseable as an RSA key (`EnableBankingConfigError`, message never includes key material).
- **Consent/callback shape (distinct from GoCardless/PayPal):** GoCardless and PayPal owner mode have their entire credential known at `start()` time. Enable Banking's flow is redirect → authorization code → a server-side `POST /sessions` exchange that only happens *after* the callback lands — this is why `OpenBankingProvider` gained a `completeCallback()` lifecycle method (identity pass-through for every other provider) and why `activateConnection()` was split into `consumePendingConnectionSetup()`/`finalizeConnection()`. See [[Provider Callback Binding]] for the full mechanism and why it doesn't weaken any of that note's existing guarantees.
- **Institution identity:** Enable Banking has no single opaque institution id — an ASPSP is identified by the compound `{name, country}` pair. `EnableBankingProvider` mints its own opaque id (`${country}:${name}`) for the picker/`institutionId` contract, decoded and re-validated against the live `/aspsps` directory in `start()` — same anti-guessing, no-`[0]`-fallback contract as GoCardless. See [[Provider Institution Selection Contract]].
- **Read-only enforcement:** `POST /auth` never sends a `payments` field — this is what actually enforces AIS-only, not directory filtering (the current docs don't confirm a `service=AIS` filter parameter's enum values, so nothing relies on one existing).
- **GnuCOBOL boundary:** routes through the same `core.validateProviderConsent`/`normalizeProviderAccountType`/`normalizeProviderAmount`/`validateProviderReconciliation` calls as every other provider. Confirmed during implementation that `VALIDATE-PROVIDER-CONSENT`'s existing generic (non-`gocardless`) branch in `core/cobol/banking/banking-core.cob` already maps Enable Banking's `AUTHORIZED` session status correctly, and the account-type/amount normalization operations take no provider argument at all — **zero COBOL source changes were needed**. See [[COBOL Domain Core]].
- **Sync pagination:** `GET /accounts/{uid}/transactions` follows `continuation_key` with `date_from`/`date_to` held identical across pages (Enable Banking's documented requirement), bounded by a safety cap (`MAX_ENABLEBANKING_PAGES`) against a provider-controlled infinite loop.
- **Sync freshness (fixed 2026-08-20):** `sync()` refreshes the account list and consent expiry from the `GET /sessions/{id}` response it already fetches for the status check, rather than the snapshot frozen at `completeCallback()` time — found by an independent `/code-review` pass on PR #142. Before this fix, an account added or removed at the bank after initial connection was never reflected, and a consent window the provider extended/shortened silently drifted from the locally cached value. Falls back to the stored values when a given response omits either field.
- **Reconnect (fixed 2026-08-20):** `start()`'s returned credential was missing `institutionId`, so a stored connection had nothing to resubmit and Reconnect was unconditionally broken for every Enable Banking connection from the moment this provider was added. Also found by the same independent review pass; fixed and covered by a "Reconnect round-trip" regression test.
- **Disconnect:** `DELETE /sessions/{id}`, idempotent on 404, never a false-positive `revoked: true` — same contract as [[GoCardless]]'s `disconnect()`.
- **Test coverage:** `server/test/enable-banking-jwt.test.js`, `server/test/enable-banking-directory.test.js`, `server/test/enable-banking-callback.test.js`, `server/test/enable-banking-sync.test.js`, `server/test/enable-banking-disconnect.test.js`, plus `server/test/open-banking-server-boundary.test.js`/`postgres-store.test.js`/`crypto-store.test.js` for the shared two-phase callback contract, and `src/features/connections/connectionsModel.test.ts`/`ConnectionsPage.test.tsx` for the frontend preference/fallback resolution.
- **Runtime verified:** no — no Enable Banking sandbox credentials configured in this environment; nothing beyond mocked `fetch` calls has exercised this code against the real API
- **Provider/device verified:** no · **Production verified:** no
- **Known blocker:** same class of gap as [[GoCardless]] — no completed end-to-end consent→sync→disconnect cycle evidenced against a live Enable Banking sandbox. Requires Control Panel setup (sandbox application, an allowed callback URL of `{APP_ORIGIN}/api/connectors/callback`, `ENABLE_BANKING_APPLICATION_ID`, and the RSA private key) before any real verification can begin.
- **Deployment wiring (added 2026-08-20) — IMPLEMENTED, NOT YET VERIFIED:** `compose.yaml`'s `connector` service now passes `ENABLE_BANKING_APPLICATION_ID` from the host environment and sets `ENABLE_BANKING_PRIVATE_KEY_FILE` to a fixed in-container path (`/run/secrets/enable-banking-private-key.pem`), populated by a read-only bind mount whose host source is `${ENABLE_BANKING_PRIVATE_KEY_HOST_FILE:-./deploy/enable-banking-private-key.placeholder}` — the placeholder (committed, no key material) keeps `docker compose up` working for deployments that leave Enable Banking unconfigured; `bind.create_host_path: false` makes a mistyped real host path fail loudly at `up` time instead of Compose silently mounting an empty directory. Documented in `.env.example`. Verified locally: `docker compose config` succeeds in both the unconfigured and dummy-key-configured cases; `docker compose create` confirms the correct mount/read-only flags in both cases and the loud failure on a bad path; actual container boot could not be exercised in this sandbox (its own Docker daemon blocks entrypoint `exec` for any image, confirmed identically on the stock `postgres` image, unrelated to this change). **Never runtime-verified**: an actual deployed connector reading a real Enable Banking key through this mount has not been observed — only `docker compose config`/`create` validation.
