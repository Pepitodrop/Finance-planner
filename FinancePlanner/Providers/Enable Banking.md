# Enable Banking (provider)

- **Implemented:** yes — real Enable Banking (https://enablebanking.com) AIS API client, `server/src/providers.js` `EnableBankingProvider`, `server/src/enable-banking-jwt.js` for RS256 application-JWT signing. Verified against current official Enable Banking docs (`/docs/api/quick-start/`, `/docs/api/reference/`) during implementation, not from memory.
- **Configured:** optional (`ENABLE_BANKING_APPLICATION_ID` + `ENABLE_BANKING_PRIVATE_KEY_FILE` or `ENABLE_BANKING_PRIVATE_KEY`)
- **Mocked:** server-side tests mock `fetch`, never a real Enable Banking sandbox call — see [[Provider Status]]
- **Role:** preferred AIS provider for normal bank connections — see [[Bank Connections]] for the Enable Banking → GoCardless preference order and fallback policy
- **Server adapter:** [[providers.js]]
- **UI:** [[Connections Page]] (bank-centric; `displayName: 'Bank connection'`, never surfaces "Enable Banking" to the user)
- **Auth model (distinct from GoCardless/PayPal):** an RS256-signed application JWT (`kid` = application id, `iss: enablebanking.com`, `aud: api.enablebanking.com`), signed fresh per request with `node:crypto` directly — no `jsonwebtoken`/`jwa` dependency added. Private key never leaves the server, never logged, resolved from a file path (preferred) or a raw env var, fails closed on anything unparseable as an RSA key (`EnableBankingConfigError`, message never includes key material).
- **Consent/callback shape (distinct from GoCardless/PayPal):** GoCardless and PayPal owner mode have their entire credential known at `start()` time. Enable Banking's flow is redirect → authorization code → a server-side `POST /sessions` exchange that only happens *after* the callback lands — this is why `OpenBankingProvider` gained a `completeCallback()` lifecycle method (identity pass-through for every other provider) and why `activateConnection()` was split into `consumePendingConnectionSetup()`/`finalizeConnection()`. See [[Provider Callback Binding]] for the full mechanism and why it doesn't weaken any of that note's existing guarantees.
- **Institution identity:** Enable Banking has no single opaque institution id — an ASPSP is identified by the compound `{name, country}` pair. `EnableBankingProvider` mints its own opaque id (`${country}:${name}`) for the picker/`institutionId` contract, decoded and re-validated against the live `/aspsps` directory in `start()` — same anti-guessing, no-`[0]`-fallback contract as GoCardless. See [[Provider Institution Selection Contract]].
- **ASPSP `group` field (confirmed 2026-08-21 against the current official API reference, `enablebanking.com/docs/api/reference/`):** the `/aspsps` response's ASPSP object carries an optional `group: { name, logo }` (`ASPSPGroup`) for cooperative banking networks — e.g. every Volksbank/Raiffeisenbank branch and every Sparkasse in a country shares one `group.name` (confirmed example: `"Volksbanken Raiffeisenbanken"`). No `service`/`psu_type` query parameter filters by group; grouping is directory metadata only, resolved client-side. `sanitizeEnableBankingAspsp()` now passes `group` through sanitized to exactly `{name, logo?}`, same allowlist discipline as every other field. See [[Bank Family Directory Resolution]] for how the frontend uses it.
- **Read-only enforcement:** `POST /auth` never sends a `payments` field — this is what actually enforces AIS-only, not directory filtering (the current docs don't confirm a `service=AIS` filter parameter's enum values, so nothing relies on one existing).
- **GnuCOBOL boundary:** routes through the same `core.validateProviderConsent`/`normalizeProviderAccountType`/`normalizeProviderAmount`/`validateProviderReconciliation` calls as every other provider. Confirmed during implementation that `VALIDATE-PROVIDER-CONSENT`'s existing generic (non-`gocardless`) branch in `core/cobol/banking/banking-core.cob` already maps Enable Banking's `AUTHORIZED` session status correctly, and the account-type/amount normalization operations take no provider argument at all — **zero COBOL source changes were needed**. See [[COBOL Domain Core]].
- **Sync pagination:** `GET /accounts/{uid}/transactions` follows `continuation_key` with `date_from`/`date_to` held identical across pages (Enable Banking's documented requirement), bounded by a safety cap (`MAX_ENABLEBANKING_PAGES`) against a provider-controlled infinite loop.
- **Three transaction-contract bugs found and fixed (2026-08-22, Mock ASPSP sandbox prep) — confirmed against the current official Enable Banking account-information API reference:**
  1. **Sign**: `transaction_amount.amount` is documented as an **absolute** (unsigned) decimal string — unlike GoCardless's `transactionAmount.amount`, which already carries its own sign. Direction comes only from `credit_debit_indicator` (`CRDT` = credit/incoming, `DBIT` = debit/outgoing). The previous code passed the absolute value straight into `core.normalizeProviderAmount()` as if already signed, silently importing every real transaction as positive income. Fixed by prepending `-` to the decimal string for `DBIT` **before** calling `normalizeProviderAmount()` — the sign is applied through the same COBOL fixed-point `NUMVAL`-based parsing path every provider already uses (confirmed `NUMVAL` correctly parses a leading `-`), never as a JS-side integer flip afterward. Fails closed (throws, never silently treated as a credit) for any `credit_debit_indicator` value other than exactly `CRDT`/`DBIT`.
  2. **Identifier**: the code preferred `transaction_id`, which is not the documented ASPSP transaction identifier — `entry_reference` is. Fixed to prefer `entry_reference`, falling back to the pre-existing deterministic `account.uid:date:amount:description` key when absent. Enable Banking's docs don't confirm `entry_reference` is unique *across* accounts (only that it's ASPSP-assigned), so it's namespaced with `account.uid` before being used as the dedup key — a shared `entry_reference` value on two different accounts can no longer cause one account's transaction to be silently dropped as a false-positive duplicate of the other's.
  3. **Status**: the code compared `item.status === 'PEND'`; the documented enum value is `PDNG` (booked is `BOOK`). `'PEND'` is not a value this API uses, so every transaction was previously imported as booked regardless of its real pending state. Fixed to compare against `'PDNG'`.
  - Verification: `server/test/enable-banking-sync.test.js` (29 cases total after this pass) — CRDT/DBIT sign correctness, entry_reference identity and its account-namespacing (including a same-`entry_reference`-different-account non-collision test), the deterministic fallback still working when `entry_reference` is absent, fail-closed behavior for an unrecognized/missing `credit_debit_indicator`, BOOK/PDNG mapping, non-EUR filtering unaffected, pagination unaffected, reconciliation still receiving correctly-signed values across a mixed set, and a GoCardless spot-check confirming its own (correct, already-signed) amount handling is untouched. A new synthetic EUR fixture (`server/test/fixtures/enable-banking-mock-aspsp-eur-dataset.json`) is exercised end-to-end through the real `sync()` pipeline as its own test case.
  - **Not yet live-verified** — these are code-correctness fixes confirmed against current official documentation and exercised only against mocked `fetch` responses in tests. No sync has ever been run against a real Enable Banking session (mock or otherwise) in this codebase's history; see [[Provider Status]].
- **Sync freshness (fixed 2026-08-20, corrected 2026-08-25 — the 2026-08-20 fix was itself buggy):** `sync()` refreshes the account list and consent expiry from the `GET /sessions/{id}` response it already fetches for the status check, rather than the snapshot frozen at `completeCallback()` time — found by an independent `/code-review` pass on PR #142. Before this fix, an account added or removed at the bank after initial connection was never reflected, and a consent window the provider extended/shortened silently drifted from the locally cached value. Falls back to the stored values when a given response omits either field.
  - **This fix itself carried a real bug, found via a live production run (2026-08-25) against Enable Banking's Mock ASPSP**: `GET /sessions/{id}.accounts` is documented as an array of bare account-id **strings**, not `AccountResource` objects like `POST /sessions` returns — but the 2026-08-20 fix treated it as objects (`account.uid`), which is always `undefined` on a string, producing requests like `/accounts/undefined/balances`. This was the exact cause of a live provider **HTTP 422** on the first sync after a real, successfully-persisted connection (see [[Provider Status]]'s Enable Banking entry for the full account-handling fix, tests, and current status).
  - Also added the same pass: Enable Banking's documented `strategy=longest` transaction request for a connection's first sync (`date_to` omitted, `date_from` sent only as a lower-bound suggestion), avoiding a `WRONG_TRANSACTIONS_PERIOD` rejection on the very first history fetch; subsequent syncs keep the existing incremental `date_from`/`date_to` window and never send `strategy`.
  - **Code-fixed, locally test-verified only** (see [[Provider Status]]) — **not yet re-verified against a real Enable Banking session**; that requires a fresh Mock ASPSP run after this PR is reviewed/deployed.
- **Reconnect (fixed 2026-08-20):** `start()`'s returned credential was missing `institutionId`, so a stored connection had nothing to resubmit and Reconnect was unconditionally broken for every Enable Banking connection from the moment this provider was added. Also found by the same independent review pass; fixed and covered by a "Reconnect round-trip" regression test.
- **Disconnect:** `DELETE /sessions/{id}`, idempotent on 404, never a false-positive `revoked: true` — same contract as [[GoCardless]]'s `disconnect()`.
- **Test coverage:** `server/test/enable-banking-jwt.test.js`, `server/test/enable-banking-directory.test.js`, `server/test/enable-banking-callback.test.js`, `server/test/enable-banking-sync.test.js`, `server/test/enable-banking-disconnect.test.js`, plus `server/test/open-banking-server-boundary.test.js`/`postgres-store.test.js`/`crypto-store.test.js` for the shared two-phase callback contract, and `src/features/connections/connectionsModel.test.ts`/`ConnectionsPage.test.tsx` for the frontend preference/fallback resolution.

## Fourth live pass (2026-08-25): Mock ASPSP discovery/authorization/callback/persistence succeed; first sync fails with provider HTTP 422

A production run against Enable Banking's **Mock ASPSP** (available in all countries, no real bank credentials needed) got further than any previous pass: discovery, authorization, and callback all completed, and an `enablebanking` connector connection was genuinely **persisted**. This is the first time this codebase has ever reached a real, persisted Enable Banking connection. The very first subsequent sync then failed with a real provider **HTTP 422**.

Root-caused (not guessed — the exact request shape was inspected against the current official API reference): `EnableBankingProvider.sync()` refreshes its account list from `GET /sessions/{session_id}`, whose documented `accounts` field is an array of bare account-id **strings** — but the code (added 2026-08-20, see the "Sync freshness" bullet above) treated it as `AccountResource` objects the way `POST /sessions` actually returns them, so `account.uid` was always `undefined`. This built requests like `GET /accounts/undefined/balances`, which the provider correctly rejected with 422.

**Fixed** (not by special-casing Mock ASPSP — a general contract fix): `session.accounts` is now read as account-id strings; an id still present from the originally-stored `POST /sessions` metadata reuses that metadata; a genuinely new id the live session now reports gets its real metadata from `GET /accounts/{id}/details` (never invented); an id the live session no longer reports is dropped from both the sync result and the persisted credential (a removed account is never treated as active merely because stale metadata still lists it); every account-id string is validated against a bounded safe-charset pattern and the whole sync fails closed on anything else, rather than guessing or silently skipping. Also added Enable Banking's documented `strategy=longest` transaction request for a connection's first sync (see the "Sync freshness" bullet above for detail) — a separate, proactively-applied fix for a `WRONG_TRANSACTIONS_PERIOD` rejection this same first-sync moment could otherwise hit next, not itself observed live yet.

**Status: code-fixed, locally test-verified only (40 tests in `server/test/enable-banking-sync.test.js`, including tests that fail without the fix and pass with it — confirmed by an independent review pass that reverted the fix, watched specific tests fail, then restored it) — awaiting a fresh Mock ASPSP run after this PR is reviewed/deployed. Do not mark the sync fix itself LIVE VERIFIED until that run happens.** See [[Provider Status]] for the full test/review breakdown.

This pass also exercised the **provider-authorization popup** (`src/providerReturnBridge.ts`, added earlier on this branch) for the first time against a real provider callback, alongside the same-tab re-unlock problem it exists to solve — see [[Provider Callback Binding]] and [[Bank Connections]] for that mechanism's own status, which is **code-fixed, not yet independently re-verified live** in the same sense as the sync fix above.

## Third live pass (2026-08-22): `POST /auth` accepted, real sandbox authentication reached

After the redirect_uri and rate-limit fixes above were redeployed, `POST /auth` was **accepted** by Enable Banking (no more `REDIRECT_URI_NOT_ALLOWED`) — confirming the canonical callback URI fix in [[Provider Callback Binding]] works far enough for the real provider. The browser reached `tilisy-sandbox.enablebanking.com/ais/` ("Authentication is initiated by Finance Planner"), then progressed to a real bank authentication-method selector (VR NetKey, PIN) for Volksbank Köln Bonn. A credential attempt was rejected by the bank sandbox itself ("Invalid credentials") — this is Enable Banking/bank sandbox UI behavior, not a Finance Planner code path, and is not evidence of any defect here.

This pass is also what motivated embedding the **official Auth Flow widget** (see [[Enable Banking Auth Flow Widget]]): the pre-auth step above currently happens on a generic Enable Banking-hosted page with an abrupt visual transition away from Finance Planner; the widget keeps that step inside the app's own modal instead.

- **Two sequential `POST /auth` bugs found and fixed this pass (2026-08-21) — do not conflate them:**
  1. **`maximum_consent_validity` unit bug** (found on the *first* live pass): `start()` compared this ASPSP field — documented as an integer number of **seconds** — directly against a day count with no conversion, so the per-ASPSP consent-duration clamp never fired. Fixed (milliseconds throughout). This fix is *why* the second live pass's request reached Enable Banking and got a real, structured response at all, instead of the earlier generic "Internal server error" — but it was **not confirmed via production logs on the first pass** (none were accessible), only via code + current official docs. Whether it was *also* independently rejecting the first live attempt (in addition to, or instead of, a redirect_uri problem Enable Banking may validate earlier in its own pipeline) cannot be fully disentangled from the evidence available — both are real, confirmed bugs regardless of which one the very first "Internal server error" was specifically reporting.
  2. **`REDIRECT_URI_NOT_ALLOWED`** (found on the *second* live pass, this time from an actual structured provider error, not a guess): `redirect_url` was built by appending `?provider=enablebanking&state=...` on top of the origin — query parameters Enable Banking's Control Panel has not registered (it validates the submitted value as an exact, bare string: `https://finance.luisbenedikt.de/api/connectors/callback` / `http://localhost:5173/api/connectors/callback`).
