# Stable Account Identity and Reconnect Reconciliation

**Found live 2026-08-26/27 (PR #154, seventh Mock ASPSP pass):** reconnecting the same real Mock ASPSP bank account produced a NEW Finance Planner account and re-imported all five historical transactions on top of it, doubling every balance/total (~€6,959.50 → €13,919.00). Root cause: account identity was keyed only to `connector:${provider}:${externalId}`, where `externalId` is Enable Banking's session-scoped `uid` — documented as "valid only until the session... is in AUTHORIZED status." A reauthorization always mints a new session, so the same real account always got a new `externalId`, which `buildSyncPreview()` (`src/connectors.ts`) treated as a brand-new account.

## The fix: a provider-agnostic stable account identity

`stableAccountId(env, provider, rawIdentifier)` in `server/src/providers.js` derives `HMAC-SHA256(CONNECTOR_MASTER_KEY, ${provider}:${rawIdentifier})` — the same secret this codebase already trusts to encrypt every provider credential — from a raw identifier the provider documents as stable across sessions:
- **Enable Banking:** `identification_hash`, confirmed against the current official API reference to be "based on the account number... can be used for matching accounts between multiple sessions (even in case the sessions are authorized by different PSUs)." Captured in `completeCallback()`'s account mapping and in `sync()`'s per-account metadata (both the `storedByUid` reuse path and the fresh `GET /accounts/{id}/details` fetch).
- **GoCardless:** `account.iban`, already referenced elsewhere in this codebase as a display-name fallback (`server/src/providers.js`'s `GoCardlessProvider.sync()`).

Never the raw value itself: the browser and Finance Planner's own encrypted cloud state only ever see the HMAC digest (`ExternalAccount.stableId` → `Account.stableId`), bounded to the same `MAX_EXTERNAL_ID_LENGTH` as `externalId` in both `server/src/user-state-store.js`'s `validateAccount()` and `src/validation.ts`'s `isAccount()`. Returns `undefined` (never throws) when the raw identifier is absent, malformed, or `CONNECTOR_MASTER_KEY` is unavailable — a sync with no trustworthy stable identity degrades to the pre-existing externalId-only path rather than fabricating one.

## Reconciliation in `buildSyncPreview()`

For each external account in a sync payload:
1. If its `externalId` matches an EXISTING account's id exactly (`connector:${provider}:${externalId}`) — unchanged, pre-existing behavior (same session, routine re-sync).
2. Otherwise, if its `stableId` matches an EXISTING account's `stableId` — this is a **reconnect**: the existing Finance Planner account id is reused (`accountsToUpdate`, refreshing `externalId`/balance/`lastSyncedAt`/`creditCard` in place) instead of creating a new one.
3. No stableId match on either side → falls through to the original create-new-account behavior. Never an unsafe automatic merge.

**Found by adversarial review (2026-08-27), fixed same pass:** step 2's match had no "already claimed this sync" tracking — two *different* external accounts sharing one `stableId` in the same payload (a realistic GoCardless case: sub-accounts documented to share one IBAN for some banks, not only an adversarial scenario) would both match the same existing account, silently merging two distinct real accounts' transaction histories into one — the same class of bug this whole fix exists to prevent, from the opposite direction. Fixed with a `claimedAccountIds` set: once an existing account id is claimed (by id or by stableId) within one `buildSyncPreview()` call, a second external account cannot also claim it — it creates its own new account instead.

The sync-selection screen (`ConnectionsPage.tsx`'s `SyncSelectionScreen`) labels a reconnect-matched row "Already in Finance Planner — refreshing balance" instead of presenting it identically to a genuinely new account — found during design review: a safe-but-silent reconciliation is still a UX defect if the user can't tell it isn't creating a duplicate.

## A second identity: `stableTransactionId` (fixed 2026-08-27, independent review, "Blocker 3"; corrected 2026-08-27, third independent review)

Reusing the reconnect-matched account's id made the pre-existing `transactionFingerprint()` (accountId + date + amountCents + normalized description) function as the de facto reconnect-dedup key. That fingerprint can collapse two **genuinely different** same-day/same-amount/same-description transactions (e.g. two identical REWE purchases) — exactly the failure mode a prior requirement said this fix must not reintroduce.

`stableTransactionId(env, provider, accountStableId, transactionReference)` in `server/src/providers.js` derives `HMAC-SHA256(CONNECTOR_MASTER_KEY, ${provider}:${accountStableId}:${transactionReference})` from a bank-assigned transaction reference, **namespaced under the account's own proven-stable identity, never the session-scoped account/requisition id**:
- **Enable Banking:** `entry_reference`. **Corrected 2026-08-27** — the original claim above ("does not document this as cross-session stable") was based on incomplete evidence from an earlier fetch of Enable Banking's API reference page. Enable Banking's own FAQ (`enablebanking.com/docs/faq/`, fetched and quoted directly) states, verbatim: *"for accounts with the same identification hashes, the value is immutable. Therefore, it can reliably be used to match transactions across different sessions when they refer to the same account at the ASPSP side."* The same FAQ documents the real caveat this codebase already handles conservatively: *"this is unfortunately not the case for all ASPSPs. Some do not provide transaction entry references at all, and some provide duplicate values even though they should not."* Also confirms `transaction_id` (a *different* field) should NOT be used as a stable reference since it can change on re-retrieval — this codebase has always used `entry_reference`, never `transaction_id`.
- **GoCardless:** `transactionId`/`internalTransactionId` — **corrected 2026-08-27**, this codebase previously computed a `stableTransactionId` for GoCardless on the same "bank-assigned, not session-scoped" reasoning as Enable Banking. New evidence found by independent verification contradicts this: a real GoCardless status-page incident ("UNICREDIT_BACXROBU internalTransactionId will change") and a corroborating firefly-iii GitHub issue (#10914, describing the id as "unique within an account, not globally across accounts" and able to change across retrievals) show GoCardless does not offer the same durability guarantee. GoCardless transactions now **never** get a `stableTransactionId` (`GoCardlessProvider.sync()` always sets it to `undefined`) — reconnect dedup for GoCardless falls back to the conservative "no trustworthy identity, preserve multiplicity" path below.
- **PayPal:** deliberately not given a `stableTransactionId`. PayPal's owner-mode connection has no per-consent reconnect flow analogous to Enable Banking/GoCardless (no `stableAccountId` concept exists for it either) — there is no reconnect-duplication bug to fix here, so none was introduced.

**The fuzzy fingerprint fallback was removed entirely as authoritative dedup evidence, for every account (2026-08-27, third independent review, superseding the "skip fuzzy fallback only for reconnected accounts" compromise above).** `buildSyncPreview()`'s transaction loop now checks, in order, ONLY: (1) exact `id` match (same-session re-sync — also the point at which a legacy transaction lacking `stableTransactionId` gets it backfilled, see below); (2) if the incoming transaction has a `stableTransactionId`, exact match against known transactions' own `stableTransactionId` — authoritative, never fuzzy. When neither applies, **the transaction is imported, never dropped** — date/amount/description are no longer treated as proof of duplication under any circumstance, reconnected or not. `transactionFingerprint()` itself was not deleted — `src/statementImport.ts`'s unrelated manual CSV/bank-statement import flow has no provider identity at all to rely on and legitimately still uses it there — it is simply no longer authoritative for the provider-sync path.

Server-side, `EnableBankingProvider.sync()`'s and `GoCardlessProvider.sync()`'s synthetic fallback key (used only when no provider transaction reference is present) previously used a `seen` Set to deduplicate that synthetic key directly — silently collapsing two real, distinct transactions sharing the same account/date/amount/description **before `buildSyncPreview()` ever saw more than one row**. Fixed with a per-`sync()`-call `occurrenceCounts: Map<string,number>` that appends an incrementing ordinal suffix instead, so every real occurrence survives; the ordinal is explicitly documented as not a stable cross-call identity. **The first pass at this fix (mid-turn) only touched `EnableBankingProvider.sync()`, missing the identical bug in `GoCardlessProvider.sync()` — found by a follow-up adversarial review of the same diff and fixed in the same pass.**

`Transaction.stableTransactionId` / `ExternalTransaction.stableTransactionId` (both optional strings) were added to the domain model, the server's `validateTransaction()` allow-list, and the frontend's `isTransaction()` guard — same bound (`MAX_EXTERNAL_ID_LENGTH`) and "absent is valid, present-but-malformed fails closed" contract as every other stable-identity field in this codebase.

## Routine refresh and legacy-identity backfill (fixed 2026-08-27, third independent review, "Blockers 1 and 2")

**Blocker 1 — a routine "click Refresh" applied nothing.** `buildSyncPreview()`'s exact-id match (`existingById`, i.e. same connection, no reauthorization) previously just `continue`d without producing any update, and `ConnectionsPage.tsx`'s `synchronize()` only ever applied anything when `accountsToCreate`/`accountsToUpdate` were non-empty — so an ordinary refresh of an already-connected account could silently fail to update its balance or import a genuinely new transaction, with the UI reporting "No new accounts were found." **Fix:** a third `SyncPreview` bucket, `routineAccountUpdates`, populated for exact-id matches (refreshed balance/creditCard/institutionId/lastSyncedAt) — applied automatically and immediately in `synchronize()`, never gated behind the "Choose accounts" selection screen the way a genuinely new or reconnected account correctly still is, and never re-applied a second time when the user later confirms a selection for other accounts in the same sync batch.

**Blocker 2 — legacy accounts/transactions never got backfilled with `stableId`/`stableTransactionId`.** Since these fields were introduced after earlier live imports, an account imported before them has no way to be recognized on a later genuine reconnect (new provider session id) — the old exact-id-match fast path discarded the incoming `stableId` rather than adopting it. **Fix:** the `routineAccountUpdates` path now backfills `stableId` (`existingById.stableId ?? external.stableId`) onto the SAME existing account, never minting a duplicate; symmetrically, an exact-id-matched existing transaction lacking `stableTransactionId` gets it backfilled via a new `transactionsToUpdate: Pick<Transaction,'id'|'stableTransactionId'>[]` bucket — carrying ONLY the id + stableTransactionId, never economic fields, so a routine refresh can never silently rewrite what a transaction recorded. Verified end-to-end by a two-phase "TEST LEGACY UPGRADE" test: phase 1 (same session) backfills; phase 2 (simulated new authorization, same identification-hash-derived stableId) reconnects via the now-populated stableId, reusing the same Finance Planner account with no duplication.

**Unreconciled legacy accounts.** When an existing provider account for this connection can be matched neither by exact id nor by stableId (the "safe backfill impossible" case — e.g. the old session already expired before ever getting a same-code routine sync), it is surfaced via `SyncPreview.unreconciledLegacyAccounts` rather than silently merged or silently ignored — rendered as an explicit warning directly on the Choose-accounts screen, since that's the moment the user is about to decide whether to import a possibly-duplicate new account.

**Found and fixed by adversarial review of the same diff, same pass:** the first version of `unreconciledLegacyAccounts` scoped its "belongs to this connection" check by `connector:${provider}:` id prefix only — which encodes the *provider*, never the specific *bank connection*. **Corrected 2026-08-27 (fourth independent review):** the credential store keys a stored connection as `connections[userId][provider]` (one row per user+provider, confirmed in `crypto-store.js`), so a user cannot hold two SIMULTANEOUS connections to the same provider — the realistic trigger is sequential: disconnect Bank A (keeping its accounts/history locally; see [[Bank Disconnect Flow]]), then connect Bank B through the same provider. Syncing Bank B would have flagged Bank A's untouched local accounts as "unreconciled" purely because they share one provider. Worse, an account whose owning connection the user genuinely disconnected but which lacks a `stableId` would nag on every future same-provider sync forever, with no way to silence it — "Remove account" itself requires the very `stableId` this class of account never has (a gap the fourth independent review also closed — see "Legacy local account removal" below). **Fixed** by narrowing the match to `institutionId` equality between the account and the connection (both already carry it) — when either side lacks `institutionId`, the account is conservatively NOT flagged, trading a rarer missed-ambiguity case for eliminating both false-positive classes.

## institutionId propagation (fixed 2026-08-27, fourth independent review, "Blocker 1")

The `institutionId`-equality guard above is only as good as the data it compares — and a fourth independent review found the guard was effectively **inert for every real bank sync**: neither `EnableBankingProvider.sync()` nor `GoCardlessProvider.sync()` ever set `institutionId` on the `ExternalAccount` objects they return, so a real sync always produced `Account.institutionId === undefined` on both sides of the comparison, which the guard deliberately never flags (to avoid a false positive when ambiguous). The guard was therefore correct in design but never actually fired outside hand-constructed test fixtures that happened to already include `institutionId`.

**Fix:** `withConnectionInstitutionId(accounts, storedInstitutionId)`, a new pure function in `server/src/account-exclusions.js`, called from `server.js`'s `buildSyncPayload()` as `withConnectionInstitutionId(filtered.accounts, stored.institutionId)` — enriching every returned account with the value already captured and validated against the live provider directory at connection time (`stored.institutionId`, the same field `connection()` already exposes read-only to the client), only when the adapter itself didn't already set a more specific one. Deliberately reads from the already-authorized **stored** connection object, never anything in the current sync request, so a client cannot manipulate `institutionId` to suppress a legitimate ambiguity warning. Never fabricates a value: if the stored connection itself has no `institutionId` (verified this never happens today, but the function does not assume it), the account's `institutionId` stays `undefined`, exactly like before.

Extracted into `account-exclusions.js` (alongside the pre-existing `applyAccountExclusions()`) for the same reason that function was extracted there: `server.js` calls `server.listen()` unconditionally at import time, so nothing defined inside it can be imported by a test without starting a real HTTP server — this pure mapping needed to live outside it to be directly unit-tested against the real production account shape (Enable Banking/GoCardless-shaped fixtures with no `institutionId`, not a hand-rolled shape that already has one).

## Legacy local account removal (fixed 2026-08-27, fourth independent review, "Blocker 2")

**This is not theoretical — it describes this codebase's own actual state.** Earlier live PR #154 heads imported the Mock ASPSP account before `Account.stableId` existed, and the seventh live pass's reconnect bug (see above) created a genuine duplicate account before the reconnect fix landed. Both classes of account persist in real cloud state today as provider-linked `Account` rows with `externalId` present but `stableId` absent — and the routine-refresh backfill (above) can only upgrade the ONE account whose CURRENT provider `externalId` still matches; a stale duplicate from an older session has no way to ever gain a `stableId`.

Dashboard's modern removal path (`removeAccount()` in `App.tsx`) correctly REFUSES to remove any provider account without a `stableId` — it has no trustworthy key to durably exclude the account by, so promising "will not be automatically re-imported" would be a lie. But with no removal path at all offered for that class of account, the exact duplicate this codebase's own earlier bug produced became **permanently undeletable from the Dashboard**, even though removing accounts from the Dashboard is an explicit product requirement.

**Fix — two clearly distinct removal semantics, never blurred together:**
- **Modern (`stableId` present):** unchanged — durable exclusion first, then local removal; survives reconnect; Restore available from Connections; confirmation truthfully promises "will not be automatically re-imported."
- **Legacy (`stableId` absent) — NEW, `removeLegacyAccountLocally()` in `App.tsx`:** an explicit, deliberately WEAKER, **local-only** cleanup. Reuses the exact same `removeAccountFromState()` domain helper the modern path already uses (atomic account+transaction removal — not a new domain operation, only a new caller of an existing one) but writes **no** `connector_account_exclusions` row and makes **no** suppression guarantee. Refuses (fails closed) for a manual account or for any provider account that DOES have a `stableId` — that class must always go through the modern path. Dashboard's confirmation dialog for this path is titled "Remove legacy account" and offers "Remove local copy," with copy that explicitly says the account "does not contain a stable bank identifier" and Finance Planner "cannot guarantee the bank will not return it again during a future sync" — **never** phrased as, or confusable with, durable exclusion. Still offers "Go to Connections to disconnect the bank instead" as an alternative action.

**Never claim the legacy path is durable exclusion.** If the provider returns an indistinguishable account on a future sync (no `stableId` to recognize it by), it may resurface, and the user may need to remove it again or disconnect the bank entirely — this is the honest tradeoff of removing an account Finance Planner cannot durably suppress, not a bug to be silently patched over with a fabricated identity or fuzzy matching.

Verified end-to-end with the exact "current duplicate recovery" scenario this fix exists for: two provider accounts (A, stale session; B, current session) both lacking `stableId`, both representing the same real Mock account. A routine sync of the current connection backfills `stableId`/`stableTransactionId` onto B only, in place, leaving A completely untouched (no auto-merge, no auto-delete). The user then removes A via "Remove local copy" — only A and its own transactions are removed, B is unaffected, no exclusion row is written, the cleanup persists through the normal cloud-save path, and a genuine reload of the saved state keeps A gone.

## Durable suppression: Dashboard "Remove account" (revised 2026-08-27 — see below)

Removing a provider-linked account (`src/features/dashboard/Dashboard.tsx`, domain logic in `src/accountState.ts`'s `removeAccountFromState()`) records a durable exclusion keyed by the account's `stableId`, so future syncs of that connection never re-import it. See [[Bank Disconnect Flow]] for how this interacts with disconnect.

### Coordinated removal (fixed 2026-08-27, independent review, "Blocker 2")

**Original defect:** `App.tsx` removed the account from local state FIRST, then fired `void excludeProviderAccount(...).catch(() => {})` — fire-and-forget. A network failure left the account "removed" in the UI (and the confirmation dialog had already told the user it would never come back) while the server never actually recorded the exclusion; the very next sync could resurrect it. Separately, a provider account with **no `stableId`** was still removable even though there is no trustworthy key to durably exclude it by.

**Fix:** `App.tsx`'s `removeAccount(account)` is now a single coordinated async operation. For a provider-linked account: (1) refuse immediately if `account.stableId` is absent — Dashboard pre-empts this even earlier, before offering any destructive action at all, via `removeTargetCannotBeRemovedSafely`; (2) `await excludeProviderAccount()` — the durable, connection-independent exclusion write (see below) — **before** touching local `AppState` at all; (3) only on success does the account/its transactions actually leave local state. On failure, local state is untouched and the caller receives `{ok:false,error}`. Dashboard's confirmation dialog shows a "Removing account…" busy state (both buttons disabled, no duplicate submission possible) and, on failure, an inline actionable error — re-clicking "Remove account" retries the same coordinated operation. Manual accounts remain synchronous/local-only (no server exclusion to coordinate with) and keep the short-lived Undo toast; provider accounts never get Undo, since a real server-side exclusion has already been recorded by the time Undo could be pressed.

The Dashboard confirmation copy ("This account will not be automatically re-imported...") is only ever shown on the path that can actually make that promise true.

### Durable, connection-independent exclusion storage (fixed 2026-08-27, independent review, "Blocker 1")

**Original defect:** exclusions were stored as `excludedStableAccountIds` inside the SAME `connector_connections` row that `DELETE /api/connectors/:provider` (disconnect) deletes and a subsequent reconnect recreates from scratch. A full disconnect + reconnect of the same real bank therefore silently lost every exclusion — directly contradicting the requirement that a removed account survive reconnect of the same economic account. The PR description at the time incorrectly called this an accepted limitation; it is not.

**Fix:** a dedicated `connector_account_exclusions` table (migration 011), independent of `connector_connections`:

```sql
CREATE TABLE connector_account_exclusions (
  user_id text NOT NULL,
  provider text NOT NULL CHECK (provider IN ('gocardless','finapi','paypal','enablebanking')),
  stable_account_id text NOT NULL CHECK (stable_account_id ~ '^[a-f0-9]{64}$'),
  account_name text,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, provider, stable_account_id)
)
```

`server/src/database.js`'s `addAccountExclusionMethods(store, pool)` attaches `addAccountExclusion`/`removeAccountExclusion`/`listAccountExclusions` onto the already-unified `store` object (mirroring the pre-existing `addWebhookEventState()` pattern), backed by this table for the Postgres driver and by a parallel `accountExclusions` structure inside `EncryptedStore` (`server/src/crypto-store.js`) for the file driver. `addAccountExclusion()` is `INSERT ... ON CONFLICT (user_id, provider, stable_account_id) DO NOTHING` — atomic and idempotent, no read-modify-write lost-update race. `account_name` is a non-sensitive display label captured at removal time (never a raw IBAN/account number) so the Restore UI (below) can show something meaningful.

`server.js`'s `buildSyncPayload()` now calls `store.listAccountExclusions(user, provider)` and feeds the plain array to `applyAccountExclusions()` (`server/src/account-exclusions.js`, now decoupled from the credential object entirely) — the filtering still happens server-side, before excluded account/transaction data ever reaches the browser. Disconnecting deletes only `connector_connections`; the exclusion row is untouched and is consulted again the moment the same real account resurfaces after a reconnect (matched by the same `stableId`, independent of the new session's `externalId`).

Account deletion (`server/src/account-deletion.js`) and the factory-reset script (`server/scripts/factory-reset.mjs`) were both updated to also clear this table — a full account/data wipe must not leave orphaned exclusion rows behind.

### Restore ("un-remove") — never an irreversible hidden tombstone

`DELETE /api/connectors/:provider/exclusions/:stableAccountId` deletes the exclusion row (`removeAccountExclusion()`), nothing more — it does not guess old local transactions back into existence. `listStoredConnections()` attaches each connection's `excludedAccounts` (stableAccountId + optional display name + `createdAt`, never a secret) so the Connections page's "Manage connection" screen (`ConnectionsPage.tsx`'s `AttentionScreen`) can render a "Removed accounts" list with an individual Restore button per account. Restoring only clears the suppression; a subsequent normal sync is what actually re-imports the account through the ordinary, reviewed import path (`buildSyncPreview()`).

## A second review round the same day found and fixed one more real regression

**"Removed accounts / Restore" silently disappeared after every sync.** `buildSyncPayload()` (the function behind both a manual "Refresh all" and the automatic post-provider-return sync) replaced `ConnectionsPage.tsx`'s entire `connections` array with its own response, but only `listStoredConnections()` (the mount-only `GET /api/connectors/connections` overview) attached `excludedAccounts` — so the Restore list vanished the instant a user synced, exactly the moment they were most likely to check it, even though the exclusion itself remained fully enforced server-side the whole time. **Fixed** by fetching `store.listAccountExclusions()` once per provider in `buildSyncPayload()` and attaching it to every connection object that function returns, on both its success and per-provider-failure branch.

A related, lower-severity UX gap found the same pass: `ConfirmationDialog`'s Escape/backdrop-click handlers call `onClose` unconditionally, bypassing the `busy` guard the Cancel/Confirm buttons already respect — dismissing the dialog while a removal was in flight could cause a later failure's error message to fire into an already-closed dialog and be silently lost (no data-integrity impact; a success still applied correctly either way). **Fixed** by guarding Dashboard's `onClose` with the same `removeBusy` check.

## Accepted non-issue

- **No backfill migration exists for the original (now-replaced) `excludedStableAccountIds`-inside-the-credential design.** This is confirmed harmless: that design was never live-deployed against real user data before this same-day fix replaced it, so no exclusion could ever have existed in that shape to migrate. The stale field name is not even read anymore; each provider's `sync()` still spreads `{...credential}` into the stored row, so an old key would ride along inertly if it somehow existed, but `applyAccountExclusions()` never looks at it.
- **Exclusion writes across two DIFFERENT accounts of the same connection do not race** — each is its own row (`INSERT ... ON CONFLICT (user_id, provider, stable_account_id) DO NOTHING`), verified against real Postgres with concurrent inserts on both the same and different `stableAccountId`s.
- **`transactionsToUpdate` (identity-only backfill) applies immediately regardless of whether its owning account's reconnect is later confirmed or cancelled on the Choose-accounts screen** (raised by adversarial review, 2026-08-27, third independent review pass). Accepted as-is: the backfill only ever adds a `stableTransactionId` to an EXISTING local transaction — never new data, never an economic field — so even if the user cancels the reconnect it was associated with, nothing is misrepresented or duplicated; the alternative (deferring backfill until the selection screen is confirmed) would add real complexity to prevent a purely cosmetic non-issue.
- **Enable Banking/GoCardless pagination overlap re-importing a synthetic-key transaction twice** (raised by the same review pass): `occurrenceCounts` is deliberately scoped to one `sync()` call, so if a provider ever returned the same transaction row twice across overlapping pages, it would now import twice instead of being caught by the old (correctness-breaking) `seen`-Set dedup. No evidence either provider's documented `continuation_key`/pagination contract can actually overlap; accepted as a documented, evidence-based limitation rather than spending complexity defending against an unobserved failure mode.
- **`removeLegacyAccountLocally()`'s (and the pre-existing `removeAccount()`'s) `setState` updater can throw if the target account is no longer present in the CURRENT state** (raised by adversarial review, 2026-08-27, fourth independent review pass): both call `removeAccountFromState()`, which throws when the account isn't found, inside a React state updater — a theoretical race if something else removed the same account between the confirmation dialog opening and the user confirming. This is a pre-existing pattern shared by the already-shipped modern removal path, not something this pass introduced; Finance Planner is single-user/single-session per browser tab with no other code path that removes an account concurrently with an open confirmation dialog, so it is accepted as a latent-but-unreachable case rather than a real defect worth hardening in this pass.
